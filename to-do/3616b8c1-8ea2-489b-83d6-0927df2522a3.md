# Plan: Append raw user feedback to a saved plan

## Problem

Users need to type or dictate feedback on a saved plan and append that text to the bottom of its Markdown file, under a header identifying it as feedback from the user. Preserve the submitted wording exactly; do not summarize, correct transcription, rewrite the plan, or invoke an agent to interpret it.

The clarified task supersedes the earlier version of this plan, which proposed automated plan revision, durable submission snapshots, and a Planned → Next transition. Those additions are outside this request.

## Scope and acceptance contract

1. On Mac, show a labeled multiline “Plan feedback” editor in task detail for an incomplete task in Planned with a saved plan. Use the hint “Enter text or dictate to provide feedback on the plan.” Provide one explicit “Append feedback” action.
2. Use the native text editor and system dictation. The user may edit the transcription before saving. Enter inserts a newline; finishing dictation does not submit. No custom microphone button, audio recording, speech service, or dependency is required.
3. Append a Markdown level-two header with the exact text `User feedback on the plan`, then a blank line, then the submitted text. Insert only the separator newlines needed between the existing document, header, and raw text. Preserve all existing file bytes and all submitted text, including leading/trailing whitespace, spelling, punctuation, Markdown, Unicode, and line breaks. Trim only a copy for empty-input validation. Do not add bullets, quotations, code fences, timestamps, or editorial commentary to the transcript.
4. Each deliberate submission appends a new labeled section at the end, preserving earlier feedback in order. Repeated identical text may be intentional; prevent duplicate clicks for one in-flight operation rather than deduplicating by text.
5. On verified success, clear only the submitted draft and show “Feedback appended to plan.” On failure, retain the draft and show an actionable error. Saving feedback does not change the task stage, completion, notes, run history, or automation setting and does not call Codex.
6. The destination is the task's saved `planPath` inside its owning project's directory, including valid noncanonical Markdown paths. Do not assume the task UUID filename or the currently selected project's directory.
7. This increment is Mac-local. On iPhone, explain that adding feedback to the Mac's plan requires the Mac until pairing/file access exists; do not expose a submit button that cannot deliver. No sync, plan regeneration, active-run steering, persistent draft library, new stage, or task-completion behavior is included.

## Implementation steps

### 1. Add a focused plan-file service

Add a small Foundation-based service, for example `Sources/StageChaseCore/PlanFileStore.swift`, so filesystem behavior can be tested using temporary directories through the existing SwiftPM target. Keep it independent of SwiftUI, SwiftData, and the runner.

Extract or reuse the rules from `CodexRunner.safePlan` in one shared resolver without weakening the runner's existing validation. Validate an existing absolute project directory, a nonempty relative `.md` path, no `..` components, and symlink-resolved containment. Require an existing regular, readable UTF-8 plan with non-whitespace content. Reject missing files, directories, escaping symlinks, invalid encoding, and inaccessible targets visibly; never create a replacement plan or directory implicitly.

Return a snapshot identifying the resolved target and original bytes. Build the suffix separately and append its UTF-8 bytes to the original data, rather than decoding/re-encoding the original file. This preserves the original prefix exactly, including CRLF or a UTF-8 BOM. Choose separator newlines consistent with the existing document where practical, without normalizing the user's text.

Serialize writes per destination, coordinate file access with Foundation file coordination, and recheck target identity and content immediately before an atomic replacement. If the snapshot differs, reject the stale append, retain the draft, and ask the user to review/retry against the latest file. Preserve normal file permissions. Atomic replacement protects against partial writes, but coordination cannot guarantee conflict prevention against arbitrary noncooperating external editors; document and test the supported conflict behavior without claiming universal locking.

### 2. Wire a local append action in AppModel

Add an async action accepting task ID, expected task revision, and submitted text. Resolve the owning project from that task. Verify the task still exists, remains incomplete and Planned, references the reviewed path, and has no active run. Do not require automation to be enabled; this is a local document edit.

Keep an in-flight guard covering the whole read/validate/write operation, and disable stage transitions, path edits, and repeated submission for that task while it is pending. Revalidate task/project identity after asynchronous reads before writing. Perform file I/O outside the main UI executor through the service.

Do not route this operation through `.move`, `.retry`, `kickRunner`, or a new AgentRun. Avoid creating a second authoritative feedback copy in SwiftData. Report success only after the write succeeds and the saved content is verified. If verification is uncertain after a possible write, keep the draft and instruct the user to inspect the plan before resubmitting; do not automatically retry and risk duplicating the append.

### 3. Add the native feedback composer

Update `TaskDetail` in `Sources/StageChaseUI/DetailViews.swift`, using its existing semantic typography and spacing. Keep feedback separate from task notes. Support native selection, copy/paste, undo while editing, accessibility labeling, and system dictation.

Disable Append feedback for empty/whitespace-only input, unsaved title/notes/plan-path changes, invalid plan availability, active runs, and an in-flight append. Explain disabled states where useful. Capture an immutable submission string at click time; either lock the editor during saving or preserve any subsequent user edits when clearing the submitted draft.

Keep unsaved drafts keyed by task ID in the app session so selection changes cannot mix or erase feedback; discard them only through an explicit discard action or verified submission. Durable recovery of an unsent draft after app termination is outside scope and must not be promised. Opening a task or refreshing runner state must not replace an unsent draft. Keep preview libraries from writing real project files.

After saving, retain the existing Open plan action so the user can inspect the appended section. No extra confirmation dialog is needed for the clearly labeled append action itself. Existing runner approvals and stage-transition confirmations remain unchanged. Task undo should not pretend to undo this external file operation.

## Risks

- **Text alteration:** Use the exact reviewed editor string. Neither transcript glossary normalization nor model rewriting applies to stored raw feedback.
- **Wrong file or lost edits:** Resolve task/project ownership and symlinks, reject stale task/file snapshots, preserve original bytes, and use serialized coordinated atomic writes. Retain feedback on all errors.
- **Duplicate append:** Block repeated submission while pending and never retry automatically after an uncertain write. Intentional later submissions remain allowed.
- **Plan Markdown rendering:** User text may contain headings or markup. Preserve it as requested; the header establishes provenance, without promising escaped/plain-text rendering in Markdown viewers.
- **Dictation availability:** System settings and language determine availability. Typing must always work; actual dictation requires visible native verification.
- **Existing worktrees and phone locality:** Appending affects only the saved source plan, not a prior run's copied plan or another device. Do not add hidden synchronization or restart existing work.
