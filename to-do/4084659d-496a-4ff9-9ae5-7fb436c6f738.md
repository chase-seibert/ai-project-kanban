# Mac–iPhone project and task synchronization

Implementation plan for task `4084659d-496a-4ff9-9ae5-7fb436c6f738`, September 29, 2026. Local Wi-Fi implementation is in progress and device acceptance remains open. This document does not mark the task complete.

## Problem and current behavior

The intended experience is one shared library: opening the iPhone app shows the Mac's projects; adding, editing, moving, and ordering tasks on either device is reflected on the other. “Sinking” is interpreted as synchronization.

Today the apps have separate local libraries. `AppModel.load()` opens each device's own `Application Support/StageChase/Library-v2.sqlite`; `LibraryRepository` explicitly disables CloudKit. There is no network service, pairing, replication, or offline command delivery. Matching project names on both devices do not identify the same project.

Verified implementation anchors:

- `Sources/StageChaseCore/Domain.swift`: stable project/task UUIDs, task revisions, rank ordering, reducer commands, and durable run records. Confirmed automated transitions must preserve the five fixed stages and manual completion.
- `Sources/StageChaseCore/Repository.swift`: actor-owned SwiftData persistence, transactional entity updates, local caching, migration, export/restore. Loading interrupts active runs; restoring disables automation. These recovery paths are unsuitable for applying phone replicas.
- `Sources/StageChaseUI/AppModel.swift`: local command dispatch, local undo, confirmation prompts, and explicit Mac runner dispatch. Its `ready` guard means foreground refresh needs a new lifecycle path.
- `Sources/StageChaseUI/{RootView,BoardViews,DetailViews}.swift`: shared project/task UI and explicit disconnected-phone messaging.
- `Apps/StageChaseMac/{StageChaseMac,CodexRunner}.swift` and `Apps/StageChasePhone/StageChasePhone.swift`: platform composition. Only Mac owns a Codex runner.
- `docs/architecture.md`, `docs/automations.md`, and `docs/project-charter.md`: Mac authority and private-network sync were the existing direction.

No existing target plan or repository session-progress artifact was found. The current source supersedes older foundation notes about JSON persistence. Git status was unavailable because this checkout has no visible Git repository; no Git changes or repairs are part of this plan.

## Scope and expected experience

1. Pair one phone with one Mac library. Mac Settings displays its connection information and a temporary pairing secret; entering that code on the phone automatically pairs without desktop confirmation. Persist the pairing so normal app opens need no setup.
2. On phone launch/foreground, immediately display cached Mac projects and refresh from the Mac when automatic syncing is enabled. While enabled, fetch changes on a short foreground interval (3 seconds) and after writes. Let the user disable automatic syncing and manually sync from Connection or by pulling down on the board. Show last successful sync and pending changes.
3. Support adding tasks to existing Mac projects, editing title/notes, moving between the five stages, and ordering within a column. Preserve UUIDs, revisions, ordering, completion state, and visible run/activity updates. Keep project creation/configuration on Mac for this first connected version.
4. Preserve changes during outages in a durable outbox. Clearly distinguish pending phone intent from Mac-accepted state. Mac must be awake, its app open, and the private connection available for new changes to be accepted. Phone background delivery is best effort, not a promised service.
5. Confirm moves that would start Codex, enforce that confirmation at the Mac, and show progress returned by the Mac. Command approvals, Stop, and explicit failed-run Retry remain on Mac for this increment; phone shows “Continue on Mac” instead of local controls that pretend to manage remote runs.

Excluded: public hosting, CloudKit/iCloud migration, Apple Reminders, custom columns, automatic completion, multi-user collaboration, multiple authoritative Macs, background daemon/login item, arbitrary remote filesystem access, and new user-facing CLI tools. Cross-project task moves are not added; “move tasks around” means stage changes and ordering within an existing project. Connected phone completion/delete/undo actions remain unavailable until explicitly supported by safe remote commands; existing Mac actions remain supported and replicate.

## Architecture and implementation steps

### 1. Establish the private transport and pairing contract

- Add a Mac service boundary (proposed `Apps/StageChaseMac/SyncServer.swift`) and shared versioned wire types (proposed `Sources/StageChaseCore/SyncProtocol.swift`). Use native networking; introduce no package dependency by default.
- User steering on September 29, 2026 initially scoped the implementation to the same local Wi-Fi, without Tailscale. On September 30, the user installed Tailscale and verified phone sync over the manual Tailscale address. Do not configure Tailscale or expose public ingress; the app does not automatically discover or advertise the tailnet address.
- Current implementation uses a bounded native TCP listener on port 47928. The framed application messages use AES-GCM encryption and authentication with a short-lived high-entropy pairing secret or a device-scoped key. The listener accepts only one phone-pairing request at a time, caps concurrent connections and message sizes, and stops with the open Mac app. This differs from the original HTTPS/Tailscale design; the wire types remain shared and versioned.
- Expose native connection settings and actionable setup/status guidance, not an application CLI. Listener starts only after explicit pairing/sync enablement, is owned by the open Mac app, and is disabled in previews/tests unless injected.
- Add a short-lived, single-use high-entropy pairing secret displayed on Mac. Protect the pairing exchange with AES-GCM; code entry itself authorizes the phone, and the Mac then issues a device-scoped random credential. Treat the code as a bearer credential and share it only with the intended phone. Store phone and Mac credentials in Keychain. Do not log credentials, pairing codes, or encrypted payloads.
- Pairing returns protocol version, persistent server/library identity, and device identity. Requests must match that library and an authorized device. Support revocation and re-pairing; stop delivery immediately on authentication failure. Rate-limit pairing attempts, cap request size/concurrency, and reject unknown versions/commands and unexpected fields. A private network alone is not application authentication.

### 2. Add transactional sync metadata and a single command service

- Keep `LibraryRepository` as the authoritative Mac writer. Extend its persistence schema deliberately for a library ID/epoch, monotonic commit sequence, device registrations, command receipts, and a bounded change journal. Preserve original stores and verify migrations before switching.
- Route Mac UI commands, accepted phone commands, and runner updates through one application command service using the same repository actor. Publish committed changes back to the shared `AppModel` immediately; a second repository instance or timer must not overwrite a stale UI snapshot.
- Add command envelopes containing protocol/library/device IDs, immutable operation UUID, client-created task UUID where applicable, typed payload, expected task revision, and any explicit automation confirmation context. Do not expose `Mutation` directly as a network API: reject client-supplied runs, activity, completion flags, plan paths, revisions, ranks, repository paths, and automation configuration outside the narrow allowlist.
- Persist the command receipt, accepted entity updates, activity/run creation, and change sequence in one transaction. A retry with the same operation ID and identical payload returns the original result; reuse with different content is rejected. Concurrent duplicates must not race. Keep receipts durable through disconnects and restarts. If receipts are pruned, retire the corresponding device/sequence window so old operations cannot execute again.
- Return typed applied/conflict/busy/confirmation-required/invalid responses. Failed persistence must leave neither an acknowledged command nor a partially queued run. A full resync or restore changes the library epoch when required so stale commands cannot overwrite restored state.

### 3. Implement consistent reads and change delivery

- Define authenticated endpoints for version/identity, initial snapshot, changes since a cursor, command submission, and operation-result lookup. Pairing is the only narrowly scoped unauthenticated flow. Reads must never dispatch commands or call the runner.
- Snapshot data and its commit cursor must describe the same repository state. For paging, use a fixed snapshot watermark/token; do not mix pages from different versions. Return bounded pages and a next cursor for incremental entity upserts and deletion tombstones.
- Include project metadata safe for phone display, tasks, public run progress/status, and bounded activity. Exclude credentials, raw approval payloads, private reasoning, and unnecessary absolute filesystem paths. Mac-only configuration remains authoritative and unwritable by phone.
- Journal all relevant Mac mutations, including project rename/create, deletion and completion on Mac, reorder changes to multiple task revisions, and runner outcomes. Preserve deterministic ordering and deterministic tie-breaking.
- Expired cursors require a fresh snapshot; phone replaces only its authoritative cache, retaining pending commands separately. Delete tombstones or snapshot absence remove obsolete cached rows without resurrecting deleted tasks.

### 4. Separate phone replication from local runner recovery

- Introduce a platform-appropriate data/service abstraction in `AppModel`: Mac local command service versus phone sync client. Proposed phone files: `SyncClient.swift` and `PhoneSyncStore.swift` under `Apps/StageChasePhone/`, injected at the phone entry point. Keep wire models platform-neutral and ensure SwiftPM/Xcode source membership remains correct.
- Persist phone authoritative cache, cursor, and outbox in SwiftData transactions. Apply downloaded records through a dedicated replica path, never `importLibrary()` or the Mac startup recovery path: phone must not disable Mac automation, interrupt Mac runs, or enqueue its own runs.
- Separate cached server state from optimistic UI overlays. Enqueue locally before showing a pending edit as saved; apply a server acknowledgement and remove its outbox record atomically. Do not run `BoardReducer.enqueue` over speculative phone changes.
- Retain the existing independent phone library unchanged. On first pairing, switch to a separately namespaced Mac replica; explain that old on-device projects remain preserved and available separately/exportable. Do not silently merge by name or upload old queued automation. Switching/unpairing must preserve unsent changes and never deliver them to a different Mac/library.

### 5. Deliver offline edits with explicit conflict handling

- Flush commands serially when connected, with bounded exponential backoff and jitter for transient failures. Preserve operation IDs across timeouts and process termination; query receipts or resend the exact operation before deciding its outcome. Refresh on foreground and stop periodic work when backgrounded.
- Queue create → edit → move dependencies in order. Later unsent intents may use a prior command's acknowledged revision only if that predecessor was accepted without intervening conflicting changes. Once an envelope is submitted, freeze it; never change a possibly accepted request under the same operation ID.
- For edits/moves, compare the expected revision on Mac. On conflict or deletion, retain the user's draft, display current Mac state, and offer discard or explicit reapply as a new operation. Never use last-write-wins or silently replace a stale revision. Pause dependent operations for that task while unrelated tasks can continue.
- For ordering, include a precondition covering the source, target, and affected column order (for example a column order revision or ordered ID/revision digest). Existing `.reorder` checks only the source revision and is insufficient for remote concurrent ordering. Reject stale order intent and show the refreshed column.
- Busy tasks remain protected by the existing active-run rules. Surface actionable busy/conflict status without repeatedly retrying a permanent error. Manual offline changes can queue; automation-triggering offline moves remain “Awaiting confirmation” until current Mac configuration/state is fetched and the user confirms while connected.

### 6. Integrate confirmed remote transitions with automation

- Before an automation-triggering move/add, display the current Mac project's automation effect and usage notice. Record confirmation for the exact operation, task revision, destination, and project automation configuration version/digest. Mac revalidates all of them; changed configuration requires a new confirmation rather than surprising the user with newly enabled automation.
- Apply a valid command and enqueue its run atomically, then explicitly invoke the existing runner after that new accepted command commits. Duplicate receipts, GET requests, refresh, cache application, and reconnection must not call `kickRunner()` or enqueue work.
- A process crash after acceptance but before/during execution retains the existing interrupted-run behavior and explicit Mac Retry requirement. Promise durable command deduplication, not exactly-once external Codex execution. Retrying delivery must not restart an interrupted run.
- Preserve Implementation plan validation, failed-run retry/session identity, explicit command approvals, and manual completion. Phone displays Needs Approval/Interrupted truthfully; no automatic approval is introduced.

### 7. Finish native UI and documentation

- Update shared Settings, project sidebar, board subtitle, task editor, and activity UI for unpaired/connecting/current/pending/offline/conflicted/revoked states. Show which Mac/library is connected and last sync time; a failed refresh is not an empty library.
- Preserve project selection by UUID across refresh. Do not dismiss unsaved task drafts or overwrite them when updates arrive. Show a changed-on-Mac indicator and use conflict resolution on save. Add accessible move/order controls on phone alongside drag-and-drop.
- In connected phone mode hide Mac-only project creation/configuration, local restore over the replica, plan-path editing, local undo, and runner mutation controls. Keep a read-only project/settings view and accurate “Continue on Mac” guidance.
- In the implementation turn update `docs/architecture.md`, `docs/design.md`, `docs/product-requirements.md`, `docs/setup-install.md`, `docs/automations.md`, `docs/decisions.md`, relevant README/AGENTS capability statements, and dated `CHANGELOG.md` entries. Do not claim sync works until verification below passes. No documentation other than this plan changes during this planning turn.

## Risks and controls

- **Network availability:** Wi-Fi changes, Mac sleep, and app lifecycle can prevent delivery. Make prerequisites visible, retain edits, and offer retry without promising always-on sync. Visible device validation remains open.
- **Data loss or cross-library contamination:** Preserve independent phone data and backups; scope cache/outbox to library identity/epoch; transactionally advance cursors; reject stale restores and wrong-library commands.
- **Duplicate paid work:** Operation receipts and confirmation validation are server enforced. Never infer work to start by scanning replicated tasks or polling. Preserve interrupted-run review after a crash.
- **Concurrent edits/order changes:** Existing single-task revisions are a useful base, but multi-record ordering and project configuration need additional preconditions. Conflicts require visible resolution.
- **Credential or code-execution exposure:** AES-GCM protected payloads, revocable device credentials, narrow commands, strict payload validation, limits, and no arbitrary paths/run mutations. The local-network listener is not TLS and must not be used on public or untrusted networks.
- **Unbounded history:** Page reads and cap journal/activity windows; specify cursor-expiry recovery and a receipt-retention protocol that cannot revive old operations.
- **Store/UI coupling:** Separate authoritative writes, replica reads, and phone overlays. Test persistence failure and runner event races so a remote write cannot leave the Mac UI stale.

### Reconnect timeout diagnosis — September 30, 2026

- The phone's saved journal has repeated 10-second timeouts to `192.168.4.26:47928`, with 638–645-byte requests and no responses. Three pending phone changes remain saved; no sync was triggered during diagnosis.
- The Mac listener is running on `*:47928`, the Mac firewall is disabled, and the Mac's `192.168.4.26/22` and the phone's reported `192.168.4.53/22` share router `192.168.4.1`. The Mac ARP table resolves the phone on Wi-Fi. The Mac journal has no phone-originated request; a local TCP probe is separately identified and is not phone traffic.
- The user confirmed StageChase is enabled under iPhone Privacy & Security → Local Network, ruling out that permission toggle. A read-only Safari TCP probe was attempted through `devicectl`, but CoreDevice timed out before the command ran; it produced no Mac request.
- The original Wi-Fi endpoint timed out before the sync frame/authentication handler. A packet capture was denied by macOS permissions, so the cause of that LAN-path failure remains unknown.
- Follow-up verification: the Mac log recorded connections from the iPhone's Tailscale address `100.117.73.114`. Three queued changes were accepted at server sequences 6, 7, and 8, followed by repeated successful refreshes reporting sequence 8. This confirms the wildcard listener works over Tailscale without a binding change. The Mac UI still advertises its Wi-Fi address only; showing the Tailscale endpoint automatically remains a possible UX improvement. Visible board propagation remains to be checked, so the broader sync plan remains in progress.
