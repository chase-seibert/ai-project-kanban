## Scope and behavior decisions

1. **Precedence:** task override → project override → StageChase global setting → built-in Latest Luna / High. Treat model and reasoning effort as one configuration pair at each level. Project and task controls offer “Use global settings” and “Use project settings” respectively; choosing an override initializes both fields from the inherited pair. Clearing it restores inheritance. There is no separate planning-versus-implementation setting in this change.
2. **Global means StageChase on this Mac.** Store the small global preference in an injected UserDefaults-backed settings abstraction, consistent with existing preferences. Do not edit the user's Codex TOML or change other Codex clients. Project/task overrides and run snapshots belong in their existing library records and exports. Global preferences are not included in library backups; document that inherited settings use the receiving Mac's global default after restore.
3. **Latest is a policy, not a permanently pinned version.** Offer “Latest Luna” alongside explicit available model choices. Resolve that policy to the newest available, nonhidden, stable Luna model from the connected Codex catalog. Prefer a documented family alias if the installed protocol provides one; otherwise recognize canonical Luna IDs and compare numeric version components (for example, 6.10 after 6.9), not lexical order, display names, or catalog order. Do not infer an unspecified alias, treat Codex's generic default as Luna, or follow an upgrade into another family. Unrecognized/ambiguous version formats require an explicit selection and a visible explanation.
4. **High is explicit.** Built-in and reset settings request `high`, regardless of the model's suggested effort. Only offer efforts supported for the selected concrete model. If High or the chosen model is unavailable, preserve the preference and show an actionable error; do not silently substitute another family, older model, or reasoning level. Revalidate when confirming work.
5. **Freeze the confirmed configuration.** Resolve and persist the concrete model ID, effort, selection policy, and source scope on each queued run in the same transaction that queues it. Global/project changes affect future runs; queued/running/history entries retain their saved pair. Display both the policy and actual model where applicable, for example “Latest Luna → GPT-6 Luna · High · Global.”
6. **Retries are reproducible.** An existing run retries using its saved pair, run ID, thread ID, and working folder. Editing a failed task's settings changes future runs, not that run's retry. The retry UI must explain this and show the saved pair. A user can start a new run with changed settings through the existing confirmed stage-transition workflow. A legacy failed/interrupted run without a snapshot must display and explicitly confirm a newly resolved pair before retry; never invent a historical model for it.
7. **Platform boundary:** model configuration controls and catalog access are Mac-only in this increment because only the Mac runs Codex. Shared Codable models preserve overrides and run snapshots on iPhone/export/restore, and run detail may display saved configuration there. Retain the clear statement that phone actions and settings do not reach the Mac; no pairing, synchronization, or phone runner is introduced.
8. Settings edits, refreshes, connection checks, imports, reads, and project switching never enqueue or start a turn. Keep the five stages, explicit stage confirmations, sandbox/approval controls, failure handling, and user-only completion unchanged.

## Risks and mitigations

- **Catalog/version ambiguity:** API documentation does not guarantee account access or catalog ordering. Use connected capabilities, numeric stable-family matching, and explicit errors; verify against the installed schema and test mixed catalogs.
- **Retry/configuration drift:** external config and resumed sessions may contain old defaults. Persist before startup and explicitly override each turn; label legacy adoption and retries clearly.
- **Persistence regression:** new required Codable properties can break all existing entities. Exercise old payload fixtures, database reload, and export/import before UI rollout; never erase or replace a failed store.
- **Confirmation races:** asynchronous catalog/settings changes could make displayed and executed choices differ. Freeze one reviewed value and retain revision checks; changes require a refreshed confirmation.
- **Confusing inheritance:** pair-based overrides are deliberate; changing global effort does not modify a task's explicitly overridden pair. Show source/effective values and make resetting inheritance obvious.
- **Connection interference:** catalog refresh and executable changes must not interrupt paid work. Share typed request handling without replacing active runner callbacks/processes; defer reconnect until idle when necessary.
- **Scope expansion:** phone sync, alternate providers, per-stage model choices, pricing UI, and new automation triggers are outside this task.
